# RAKURS v4 — історична панель HA та актуальний перехід на MySQL

**АКТУАЛЬНА ЦІЛЬОВА АРХІТЕКТУРА:** Rakurs Standalone, тільки
MySQL rakurs на 192.168.5.30 для вимірювань і всього архіву.
Home Assistant у новому Rakurs НЕ використовується. Папка
standalone/ містить власний вебдодаток (поки тільки локальний
прототип, не переключений Nginx). Подальший опис тут — історія
існуючої панелі Home Assistant до завершення переходу.

**Актуальна довгострокова БД:** MySQL `rakurs` на `192.168.5.30`.
Інструкція: `LAN_MYSQL_UA.md`. 24.11.2026 інсталятор підтвердив
`RAKURS_TABLES=5` і `RAKURS_SCHEMA_VERIFY_PASS` — п'ять порожніх таблиць
у базі `rakurs` створені. **Автоматичний запис телеметрії ще не ввімкнений.**
SQLite Home Assistant не змінюємо.


## Підтверджений фактичний стан (24.11.2026)

- TRB145 із назвою `ITM` **зараз фізично підключена до ІТМ**.
- Надалі її планують фізично перенести до Deye. До того часу
  **не змінювати** `rs_overip`, 115200/8N1, порт 50006 та служби `sodog`.
- Home Assistant і Rakurs HTTPS працюють, попередня SVG-схема відображається.
- Реальна телеметрія Deye **відсутня**, перевірка регістрів не виконувалася.
- `deye_p3.yaml` стосується *інших підмоделей* Deye; SG05LP3
  під нього **не перевірено**. Не активувати непідтверджені регістри.

## Що підготовлено

`dashboard-rakurs.yaml` — повна версія v4 із вкладками:
Огляд, Сонце, Акумулятор, Мережа, Навантаження, Інвертор, Історія,
Події, Архів, Система.

`signal_catalog.json` — машинозчитуваний каталог із
316 **планових** показників. У ньому для кожного сенсора:
українська назва, одиниця вимірювання, ідентифікатор `sensor.rakurs_*`,
відповідне ім'я у профілі `deye_p3.yaml` та статус підтвердження.

У каталог включено також **опційні 20 батарейних модулів BMS**,
бо такі групи є в референсному профілі. Це **не твердження**, що
20 модулів реально підключено. Їхні дані з'являться тільки після
виявлення та перевірки.

Вихідний профіль містить перемикачі, уставки та інші функції запису;
**карток керування немає**. Інтерфейс не створює значень, команд Modbus
та не пише у контролер. Графіки Home Assistant є умовними:
їх показуємо лише за наявності головної сутності з реальним станом.

## Де зберігаються дані

**Фактичний Docker bind mount:** Debian
`/home/ivital/deye-monitoring-src/deploy/data` ⇄ HA `/config`.

За **стандартного** Recorder/SQLite:
`/home/ivital/deye-monitoring-src/deploy/data/home-assistant_v2.db`.
Уточнення фактичної БД і її розміру потребує перевірки:

```bash
cd ~/deye-monitoring-src
git pull --ff-only
bash deploy/rakurs/audit_storage.sh
```

Це read-only аудит: перевірка точного Docker bind mount, дискового
простору, наявності конфігурації Recorder й таблиць БД без читання
сенсорів або секретів.

**Стандартне зберігання Home Assistant:** детальна історія 10 діб,
5-хвилинна статистика протягом строку зберігання, погодинна
довгострокова статистика без автоматичного очищення **лише** для сенсорів
із коректним `state_class` і включених у Recorder.

Джерела:
https://www.home-assistant.io/integrations/recorder/
https://www.home-assistant.io/docs/configuration/long-term-statistics/

### Для багаторічного архіву кожного вимірювання

Необхідна **окрема архівна база даних** або інший незалежний потік
запису; погодинна статистика Home Assistant не замінює сирі показники
кожного опитування. Схему окремої MySQL БД уже створено. Розмір/інтервал запису й
резервне копіювання на зовнішній носій — наступний етап після
перевірки реальних даних та обсягу диска.

Не ставимо `purge_keep_days: 3650` і не вимикаємо автоочищення
на спільному сервері Odoo/Ergodata; це може виснажити диск.
Не змінюємо `recorder.db_url` навмання: міграція даних між БД
офіційно не підтримується.

### Резервування

Сам факт, що файл лежить на Debian, **не є резервною копією**.
Потрібні інкрементальні/повні копії на окремому носії (наприклад NAS),
шифрування даних облікового запису та перевірка відновлення.
Для SQLite не копіюйте відкритий `.db` як простий файл, ігноруючи
журнал WAL; використовуйте HA Backup або узгоджений SQLite backup API.

## Установлення

1. На сервері `git pull --ff-only` (нові файли й документація).
2. `bash deploy/rakurs/audit_storage.sh` для read-only аудиту.
3. У панелі **«Rakurs — Енергомоніторинг»** відкрийте
   «Редагувати → ⋮ → Редактор сирої конфігурації».
4. Збережіть поточний YAML, замініть тільки конфігурацію цієї панелі
   файлом `deploy/rakurs/dashboard-rakurs.yaml`, збережіть.
5. Для відкату є `dashboard-rakurs-v3.yaml`.

Ні перезапуск Docker, ні зміни Nginx, Odoo, Ergodata чи Teltonika
для цього етапу не потрібні.

## Підготовлена структура окремого архіву (не активована)

Файл `archive_schema.sql` містить **проєкт** схеми довготривалого
архіву: пристрої, каталог сигналів, виміри з UTC-мітками, сирі значення,
статус якості, події, статистику циклів опитування.
Схему створено в окремій MySQL `rakurs`, але вона не підключає
Teltonika й не змінює Home Assistant. Реєстр показників
`signal_catalog.json` ще непідтверджений фізичним Deye.

Для запуску архіву потрібно буде погодити частоту вимірювань,
доступний обсяг зовнішнього накопичувача, відокремлену БД, обліковий
запис лише на запис, резервне копіювання та тест відновлення.
Зберігання **всього** сирого архіву поки НЕ ввімкнено.

## Історичний TLS-блокер зовнішнього MySQL (не використовується)

**Застаріло:** цю зовнішню БД скасовано; актуальна інструкція — `LAN_MYSQL_UA.md`.

Попередня зовнішня БД `kshz1_rakurs` знята з проєкту. Історичний
протокол — `MYSQL_TLS_BLOCKER_UA.md`; для нової локальної БД він
не застосовується. Для `192.168.5.30/rakurs` користувач обрав MySQL
без TLS у локальній мережі. Поточна інструкція: `LAN_MYSQL_UA.md`.

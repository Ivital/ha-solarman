# RAKURS: інвертори, параметри та автоматичне опитування

**Стан розробки:** конфігурація та агент готові до CI/приймання в GitHub. Ні
міграція БД, ні опитування обладнання не запускаються під час коміту/деплою.
Поточні записи Deye мають старий `kind=simulation`. Вони лишаються
архівними записами й **не вважаються підтвердженими живими джерелами**.

## Новий розділ «Керування»

Адміністратор із поточною авторизованою сесією та CSRF може:

- додати інвертор (унікальний незмінний ключ; необов'язковий слот Deye №1/№2);
- змінити назву, модель, серійний номер, приватну IPv4-адресу шлюза, TCP-порт;
- змінити протокол Modbus TCP або RTU-over-TCP, slave ID 1–247, функцію
  FC03/FC04, початок і кількість регістрів (максимум 8), таймаут 200–5000 мс;
- увімкнути/вимкнути окремий пристрій для опитування;
- увімкнути/вимкнути загальний режим і встановити інтервал **15–3600 с**.

Viewer має лише перегляд. Усі зміни лишаються в MySQL і проходять через
параметризований SQL, admin-роль та CSRF. Зміна адреси або профілю Modbus
скидає підтвердження фізичного підключення та вимикає загальне опитування.
При додаванні *фізичного* пристрою до слота з уже наявним історичним
`member_kind=simulation` створюється окрема реєстрація
`member_kind=physical`; історичні записи не перекласифіковуються.

**Межа:** ці форми конфігурують тільки **опитування/архівування сирих
Modbus-регістрів**. Ні прошивку, ні електричні налаштування інвертора
вебдодаток не змінює. Введення реальних значень до 316 показників потребує
окремо підтвердженої таблиці декодування регістрів для конкретної версії
прошивки Deye. Програмно згенеровані старі показники не замінюються
псевдореальними.

## Розгортання вебінтерфейсу

1. Перевірити GitHub Actions (усі CI тести) та скрипт
   `deploy_parallel_ui.sh --check`.
2. На Windows MySQL Server **до встановлення нової конфігурації** виконати
   `install_polling_config_windows.ps1` без параметрів: лише перегляд.
3. Виконати `-Apply -GitRef <ПОВНИЙ_SHA_КОМІТУ>` після того, як
   перевірено повний SQL-бекап і збережено його поза сервером. Скрипт
   створює **4 додаткові** таблиці, вимкнену за замовчуванням конфігурацію
   та мінімальні DML-права для `rakurs_web`; **не змінює** старі вимірювання.
4. Затим розгортати вебкод через `deploy_parallel_ui.sh --apply` з
   ізольованого checkout перевіреного SHA та контролем HTTPS-хешів.
5. У меню **Керування** перевірити `Автоматичне опитування: вимкнено`,
   інтервал 60 с, обидва збережені Deye, роль viewer/admin, CSRF,
   відсутність записів в історію від вебсервера.

## Агент опитування — окремий фізичний допуск

**Не запускати зараз:** конкретні порт, тип протоколу й Modbus ID
на шлюзі TRB145 не підтверджені. Особливо: Parallel CAN, BMS, Meter-485,
Modbus RJ45 — різні інтерфейси. Не змінювати електричні параметри
інвертора без уповноваженого спеціаліста.

Після фактичного обстеження й обов'язкового погодженого контрольного
зчитування:

1. Окремо створити Linux-системного користувача `rakurs-poller`.
2. Окремий MySQL `rakurs_ingest` із SELECT лише необхідних таблиць,
   INSERT лише журналу опитувань/кадрів/сирих регістрів/подій/відбитків
   та UPDATE тільки `rakurs_poll_runtime`. Обов'язково TLS із перевіркою
   сертифіката MySQL і власником секретного файла — користувач агента.
   **Не передавати ці права вебакаунту `rakurs_web`.**
3. Підтвердити обидві фізичні реєстрації: `kind=inverter`,
   `member_kind=physical`, `member_verified=1`,
   `transport_verified=1`, `modbus_address=slave_id`;
   `rakurs_device_settings.verified_connection=1` лише після протоколу.
   Це окрема контрольована операція DBA, **не кнопка інтерфейсу**.
4. Скопіювати `rakurs-poller.service` у systemd. У локальному drop-in
   **встановити точну приватну IPv4-адресу схваленого шлюза**
   `RAKURS_ALLOWED_GATEWAY_IPS`; скрипт ніколи не використовує DNS,
   не сканує мережу й не працює без allowlist. Створити дозвільний файл
   `/etc/rakurs/poller-commissioned` під контролем адміністратора.
5. Увімкнути service тільки після тесту `python -m standalone.poll_worker`
   (**без** `--run`: перевірка без мережі й записів).
6. Відкрити **Керування**: агент повинен бути онлайн, тоді адміністратор
   може ввімкнути опитування. Після вимкнення нові запити припиняються
   на наступному циклі воркера (до 2 с, крім поточного запиту, таймаут
   максимум 5 с). **Не вимикати лише через UI в аварійній ситуації:
   зупиняти systemd-сервіс або шлюз фізично відповідально.**

Кожен цикл — максимум 8 16-бітних регістрів FC03/04 **на один
підтверджений інвертор**, запис повних байтів запиту/відповіді,
перевірка Modbus TCP MBAP / RTU CRC16 та архівування лише після успіху
валідації. Немає Modbus write functions FC05/FC06/FC15/FC16, зміни BMS,
CAN або режимів інвертора.

### Штатне спостереження

`GET /api/v1/config` повертає `enabled`, `interval_seconds`,
`worker_online`, `actively_polling`, `runtime` та пристрої. Зелене
«MySQL доступна» означає лише доступність SQL; не є індикатором
фізичного з'єднання з інвертором. Дивіться `last_success_utc`
і вік останнього збереженого запису. Помилки в з'єднанні не
підміняються показниками. Старі записи у MySQL не видаляти.

### Відкат

Web UI: штатний файловий backup `deploy_parallel_ui.sh --apply`.
MySQL: повний перевірений дамп **до міграції**; міграція лише додає таблиці,
але її відкат/відновлення робити лише ізольовано, не через довільний DROP
на живій БД. Агент: `systemctl disable --now rakurs-poller.service`;
вебдодаток і два існуючі інвертори продовжують працювати незалежно.

# RAKURS — блокер автентифікації TLS зовнішньої MySQL (24.11.2026)

## Перевірені факти

- Адреса: `kshz1.mysql.tools:3306`, цільова БД `kshz1_rakurs`.
- TCP connect з `ergodata-lnx` підтверджено (`PASS`).
- MariaDB CLI 11.8.9 з обов'язковою перевіркою імені й CA повернув `ERROR 2026 (HY000): self-signed certificate in certificate chain`.
- Сервер повертає два сертифікати: автоматичний MySQL Server та самопідписаний MySQL CA.
- Leaf subject CN=`MySQL_Server_5.7.44-52_Auto_Generated_Server_Certificate`.
- Leaf issuer CN=`MySQL_Server_5.7.44-52_Auto_Generated_CA_Certificate`.
- Leaf SHA-256 fingerprint: `9F:72:9A:73:A0:1B:79:89:21:AF:09:D0:B1:E4:E4:0B:89:06:FB:34:6C:40:63:88:44:E8:06:92:85:BA:16:05`.
- CA SHA-256 fingerprint: `C4:82:C3:98:54:63:97:F9:4A:B5:4C:54:BA:CB:CB:EC:61:6E:8D:98:D6:BF:D3:5D:D8:B2:88:1D:66:7F:29:D5`.
- Leaf validity: `2025-05-13` — `2035-05-11`. Ці строки самі по собі не доводять довіру.
- OpenSSL повідомив `hostname mismatch`, код 62, а також `self-signed certificate in certificate chain`.
- За діагностичним виводом не підтверджено SAN `DNS:kshz1.mysql.tools`; поле `CN` також не відповідає імені.
- Ім'я `5.7.44-52` у сертифікаті не є незалежною перевіркою фактичної версії SQL-сервера.

## Висновок

Додавання цього неперевіреного CA до trust store саме по собі НЕ виправить невідповідність імені.
Не використовувати `--skip-ssl-verify-server-cert`, відключення TLS, `VERIFY_CA` замість перевірки імені,
чи blind trust/self-signed CA з каналу, що зараз неавтентифікований.
Авторизацію користувача, наявність таблиць і права DDL не перевірено. Не виконувати DDL.

## Обмеження послуг (потрібна перевірка тарифу)

Адреси `*.mysql.tools` згадуються в документації «Хостінг Україна»,
але фактичний тариф конкретного акаунта не перевірено. Офіційна довідка
для звичайного хостингу зазначає SSL для зовнішнього MySQL тільки на бізнес-хостингу:
https://www.ukraine.com.ua/wiki/hosting/databases/mysql/databases/credentials/

У хмарній послузі MySQL провайдер описує встановлення власних сертифікатів:
https://www.ukraine.com.ua/wiki/cloud/mysql/ssl/
Це інший продукт; не застосовувати процедуру хмарного інстансу до спільної БД без підтвердження підтримки.

## Безпечний подальший план

1. Змінити раніше розкритий пароль MySQL через панель хостингу.
2. Встановити тип послуги й узгодити з підтримкою hostname-verified TLS
   (серверний сертифікат із SAN для `kshz1.mysql.tools`, підтверджений CA),
   або автентифікований SSH/VPN тунель/перенесення на окремий MySQL instance.
3. Підтвердити актуальну версію SQL-сервера й можливість MySQL 8.4;
   не робити висновок про версію тільки з назви авто-сертифіката.
4. Тільки після виправлення сертифікатів повторити
   `bash deploy/rakurs/mysql_archive_preflight.sh --login`.
5. Далі погодити схему/права, ліміти й окрему систему резервування,
   і лише після цього створювати порожні таблиці й планувати архівний ingest.

## Стан системи

Home Assistant SQLite Recorder, Rakurs UI, ІТМ і Teltonika залишаються без змін.
Паролі не зберігалися в репозиторії. `archive_mysql_schema.sql` поки не застосовувався.

## Уточнення типу послуги (24.11.2026): бізнес-хостинг

Користувач підтвердив, що `kshz1_rakurs` розміщено саме на **бізнес-хостингу**.
Офіційна довідка підтверджує, що для бізнес-хостингу SSL зовнішніх MySQL-з'єднань підтримується:
https://www.ukraine.com.ua/wiki/hosting/databases/mysql/databases/credentials/
https://www.ukraine.com.ua/wiki/hosting/general/business/

**Але підтримка TLS-шифрування не означає наявність перевіреного
сертифіката з DNS SAN, що відповідає `kshz1.mysql.tools`.**
Наявний авто-сертифікат не проходить ані довіру до CA, ані перевірку імені.
Це вимагає виправлення на стороні провайдера або іншого автентифікованого каналу.

Важливо: документація провайдера прямо зазначає, що SSH-тунелювання
та проксування через SSH для хостингу **не підтримується**:
https://www.ukraine.com.ua/wiki/hosting/cli/ssh/connect/
Тому не пропонувати SSH-тунель на тому самому бізнес-хостингу
як готове рішення без окремого письмового підтвердження підтримки.

**Звернення до провайдера:** попросити, чи можна замінити TLS
сертифікат MySQL-сервера сертифікатом із SAN `DNS:kshz1.mysql.tools`
та надати перевірений CA; якщо ні — які підтримувані ними
способи автентифікованого TLS для зовнішнього клієнта Debian.
Додатково уточнити фактичну серверну версію MySQL (5.7 чи 8.4).
**Не змінювати версію MySQL самостійно:** документація вказує,
що зміна версії переносить усі БД хостинг-акаунта і може вплинути
на робочі сайти.

Жодне послаблення TLS, DDL або введення пароля до усунення проблеми
сертифіката не дозволяється.
